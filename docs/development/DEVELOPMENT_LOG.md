## 2026-09-17 (23) — Log 댓글 수정·소프트 삭제·관리자 복구

### 요구사항 확정

- 일반 회원은 자신의 활성 댓글만 수정·삭제할 수 있다.
- 일반 회원은 다른 회원과 관리자의 댓글을 조회만 할 수 있다.
- 관리자는 모든 댓글을 수정·소프트 삭제·복구할 수 있다.
- 댓글을 삭제해도 원문은 DB에 남기고, 일반 사용자에게만 숨긴다.
- 실제 수정이 일어난 경우에는 `수정됨`과 수정 시각을 남긴다.

### 구현

- `log_comments`에 nullable `updated_at`, `deleted_at`을 추가했습니다. 처음 작성한 댓글에는 수정 시각을 억지로 넣지 않고, 수정·삭제·복구 때만 `updated_at` 트리거가 기록합니다.
- 기존 물리 DELETE RLS 정책을 제거하고 UPDATE 정책으로 전환했습니다. 일반 회원은 자신의 활성 댓글만, 관리자는 삭제된 댓글까지 포함해 수정할 수 있습니다.
- 공개 SELECT 정책은 활성 댓글만 통과시키고, 관리자는 `is_admin()`으로 삭제 댓글 원문까지 조회합니다.
- DB 트리거가 `log_slug`, `author_id`, `author_name`, `created_at` 변경을 거부해 API를 직접 호출해도 댓글의 소속과 작성자를 바꾸지 못하게 했습니다.
- 공개 Log 상세에 수정 입력·저장·취소 UI와 수정 시각을 추가했습니다. 삭제하면 목록에서 즉시 사라지지만 실제 행은 보존됩니다.
- `/admin/comments`에는 삭제됨·관리자 전용 표기, 작성/수정/삭제 시각, 수정·삭제·복구 동작을 추가했습니다.

### 원격 권한 검증

- 다른 회원 신원: 기존 댓글 수정 0건, 물리 DELETE 0건
- 관리자 신원으로 소프트 삭제 뒤 다른 회원 신원: SELECT 0건
- 관리자 신원: 소프트 삭제된 댓글 복구 1건, 복구 시 수정 시각 기록 확인
- 테스트는 모두 트랜잭션 롤백으로 수행해 실제 댓글 데이터는 바꾸지 않았습니다.

### 검증 결과

- `npm run lint`, `npm run type-check`, `npm run format:check`, `npm run build` 통과
- 공개 Log 상세의 수정 입력·저장/취소와 관리자 댓글 목록의 수정 입력·삭제 안내를 브라우저에서 확인
- 데스크톱 관리자 화면에서 가로 넘침 없음 확인
- Security/Performance Advisor 재확인: 이번 트리거·정책에서 새 경고 없음. 기존 프로젝트 전반의 GraphQL 노출, SECURITY DEFINER 함수, 유출 비밀번호 보호, 미사용 인덱스 경고는 범위 밖으로 유지

- `src/app/admin/comments/` — 전체 또는 Log별 댓글 조회, 글·작성자·원문·등록일 표시, 관리자 삭제 액션

### 추가 및 수정

- `src/app/(site)/log/[slug]/page.tsx` — 한글 글자·영문 단어 수를 이용한 예상 읽기 시간 계산, 제목 아래에 발행일·읽기 시간 메타 정보 추가, 태그를 별도 내비게이션으로 정리

## 2026-09-16 (19) — 헤더 Admin 링크를 실제 관리자에게만 제한, 프로젝트 폼 정렬 버그 수정

### 시작 상태와 문제

`AuthNavLink`(18번 작업에서 새로 만든 컴포넌트)는 "로그인했는지"만 확인해서, `user_roles` 트리거로 자동 생성되는 일반 회원(`member`) 계정도 로그인만 하면 헤더에 "Admin" 링크가 보였습니다. `/admin` 서버 쪽 접근 제어는 항상 정상 동작하고 있었지만, 일반 회원에게 관리자 진입 링크가 노출되는 건 UX상 혼란스러운 문제였습니다. 별개로 `/admin` 프로젝트 작성 폼에서 "URL 식별자"처럼 힌트 텍스트가 있어 키가 큰 필드와 "진행 상태"처럼 짧은 필드가 같은 행에 있으면, `.admin-form-row`가 짧은 필드를 세로 중앙 정렬해 "공개 상태" 행과 다르게 보였습니다.

### 판단

서버 쪽 `/admin` 레이아웃은 이미 `isAdminUser()`로 안전하게 막고 있었으므로, 이번 수정은 어디까지나 **클라이언트에 보여주는 링크를 실제 권한과 맞추는 UX 수정**입니다. `AuthNavLink`가 로그인 여부에 더해 RLS로 허용된 본인 `user_roles` 행을 직접 조회해, `role='admin'`일 때만 "Admin" 링크를 보여주도록 했습니다. 폼 정렬은 상단 정렬로 바꿔 다른 행과 톤을 맞췄습니다.

### 추가 및 수정

- `src/components/auth/AuthNavLink.tsx` — 로그인 여부 확인에 더해 `user_roles` 조회를 추가해 `admin` role일 때만 Admin 링크 표시
- `src/styles/globals.css` — `.admin-form-row`를 상단 정렬로 수정

### 삭제

- 없음

### 초보자 설명

"서버가 이미 막고 있으니 화면에 뭘 보여줘도 안전하다"고 생각하기 쉽지만, 안 보여줘도 되는 링크를 보여주는 것 자체가 사용자를 헷갈리게 하는 별개의 문제입니다. 이번처럼 서버 권한 검사(진짜 보안)와 화면에 무엇을 보여줄지(UX)를 구분해서, 화면 쪽도 실제 데이터(`user_roles`)를 근거로 판단하도록 맞췄습니다.

## 2026-09-13 (16) — 다크 모드, 댓글 삭제 버그 수정, 댓글 UX 개선

### 시작 상태와 문제

### 판단

임시 id로 낙관적 업데이트를 하는 대신, `addLogComment`가 **DB에 실제로 삽입된 행(진짜 id 포함)을 그대로 반환**하도록 바꿔 화면과 DB의 id가 항상 일치하게 했습니다. 삭제 확인은 새로 만들지 않고 관리자 화면에서 이미 검증된 `<dialog>` 기반 확인 패턴을 `ConfirmButton` 컴포넌트로 공개 사이트 디자인 토큰에 맞춰 그대로 옮겼습니다. 다크 모드는 대부분의 색상 규칙이 이미 CSS 변수를 참조하고 있어서, 루트 토큰을 다크용으로 다시 정의하는 것만으로 사이트 대부분을 커버할 수 있다고 판단했습니다. 값이 하드코딩돼 있던 일부(그림자, 위험 버튼 배경/텍스트)만 별도 변수를 추가했습니다. 첫 렌더 전에 저장된 테마를 적용하는 인라인 스크립트를 루트 레이아웃에 넣어 라이트/다크 전환 시 깜빡임(FOUC)을 막았습니다.

### 추가 및 수정

### 초보자 설명

Supabase(PostgREST)는 외래키 하나로 연결된 "다대일" 관계(여러 글이 카테고리 하나를 가리킴)를 조회하면 배열이 아니라 객체 하나(`{name, slug}`)를 돌려줍니다. "1:N"의 반대 방향인 "N:1"이라 배열일 필요가 없기 때문입니다. 배열이라고 착각하고 `[0]`으로 접근하면 실제로는 조용히 `undefined`가 나와서, 에러 없이 잘못된 기본값으로 넘어가는 조용한 버그가 생깁니다.

## 4차 — 모바일 Hover와 Hero 점검

### 시작 상태와 문제

프로젝트와 로그 이미지는 CSS 기본값으로 항상 흑백이었고 `:hover`일 때만 컬러가 됐습니다. 스마트폰에는 마우스가 없으므로 모바일 사용자는 컬러 이미지를 볼 방법이 없었습니다. 또한 Hero 제목의 최소 크기가 54px이라 360~430px 화면에서 문장이 부자연스럽게 여러 줄로 나뉠 가능성이 있었습니다.

### 판단

터치할 때마다 컬러를 토글하는 JavaScript를 추가하면 링크 탭 동작과 충돌하고 상태도 복잡해집니다. 모든 기기의 기본을 컬러로 두고, 실제 마우스가 있는 환경에서만 흑백 효과를 추가하는 CSS 방식이 가장 단순하고 안전합니다.

### 추가

- `@media (hover: hover) and (pointer: fine)` 마우스 환경 조건
- 480px 이하 Hero/404용 모바일 글자 크기와 line-height
- 모바일 내비게이션·필터 링크 최소 40px 터치 높이
- 모바일 검색 입력·버튼 최소 44px 높이
- 누적 작업 로그 `docs/development/DEVELOPMENT_LOG.md`
- 단일 요청 관리 문서 `docs/development/DEVELOPMENT_REQUEST.md`

### 수정

- 프로젝트/로그 이미지는 기본 컬러, 마우스 환경에서만 흑백→Hover 컬러로 변경

### 삭제

### 초보자 설명

CSS 미디어 쿼리는 화면 너비뿐 아니라 입력 장치의 특성도 확인할 수 있습니다. `hover: hover`는 마우스를 올리는 동작이 가능한지, `pointer: fine`은 마우스처럼 정밀한 포인터인지 뜻합니다. 이 조건을 통과한 기기에만 추가 효과를 주면 모바일에서 기능을 잃지 않습니다.

## 6차 — 기술 블로그형 MDX 글쓰기 시스템

### 시작 상태와 문제

- 블록 사용 예시를 담은 작업 Log 템플릿

## 5차 — 배포 준비와 실제 작업 Log 정리

### 시작 상태와 문제

metadata, robots, sitemap의 기준 주소가 아직 소유하지 않은 `buildnlearn.dev`로 고정되어 있었습니다. 로컬·Vercel 미리보기·실제 도메인은 서로 주소가 다르므로 배포 환경에 따라 주소를 바꿀 방법이 필요했습니다. 모바일 검색 버튼은 폭이 좁을 때 두 글자가 나뉠 수 있었고, 사이트 Log에는 실제 작업이 아닌 placeholder 글 6개도 공개되고 있었습니다.

### 판단

사이트 URL은 여러 파일에 반복해서 적지 않고 공통 모듈 한 곳에서 계산해야 합니다. 사용자 지정 환경변수를 가장 먼저 사용하고, 없으면 Vercel이 제공하는 주소, 그것도 없으면 localhost를 사용하도록 정했습니다. Log는 학습용 예시와 실제 기록을 섞지 않고 실제로 수행한 작업만 공개하기로 했습니다.

### 추가

- 사이트 URL 우선순위를 관리하는 `src/lib/site.ts`
- GitHub 연결부터 환경변수·도메인·배포 후 점검까지 설명한 `docs/deployment/DEPLOY.md`
- Node 24.x 실행 환경을 알리는 `package.json`의 `engines`
- 이번 작업을 기록한 5차 MDX Log
- `next.config.ts`에 미래의 외부 이미지 도메인 등록 위치 안내

### 수정

- layout, robots, sitemap이 같은 `SITE_URL`을 사용하도록 통합
- 검색 버튼에 최소 너비, 좌우 여백, 줄바꿈 금지 적용
- 작업 Log 템플릿에 직접 수행하거나 확인한 사실만 적도록 원칙 보강

### 삭제

- 실제 경험을 기록한 글이 아니었던 placeholder Log 6개
- 삭제한 예시 Log에서만 사용하던 SVG 이미지 5개
- 코드에 직접 적혀 있던 미확정 `buildnlearn.dev` 주소

### 초보자 설명

환경변수는 코드를 고치지 않고 실행 장소마다 다른 값을 넣는 설정입니다. 로컬에서는 `localhost`, Vercel에서는 자동으로 만들어진 주소, 나중에는 구매한 도메인을 사용할 수 있습니다. URL을 한 파일에서 정하면 metadata와 검색엔진용 파일이 서로 다른 주소를 가리키는 실수도 줄어듭니다.

### 검증 결과

- `NEXT_PUBLIC_SITE_URL` → `VERCEL_URL` → localhost 우선순위를 각각 확인했습니다.
- 390px에서 검색 버튼은 64×46px이고 `검색`이 한 줄로 표시됐습니다.
- 가로 스크롤은 없었고 metadata의 OG 이미지, robots, sitemap은 모두 localhost 주소를 사용했습니다.
- 공개 Log에는 1~5차와 템플릿 정비 기록까지 실제 작업 Log 6개만 표시됐습니다.
- 브라우저 콘솔 오류·경고가 없었습니다.
- `npm run lint`, `npm run type-check`, `npm run format:check`, `npm run build`를 모두 통과했고 빌드 경고도 없었습니다.

## 로그 템플릿 정비 — 사이트에 실제 작업 기록 남기기

### 시작 상태와 문제

`docs/development/DEVELOPMENT_LOG.md`에는 개발 과정이 있었지만 실제 사이트의 `src/content/logs/`에는 예시 글 6개만 있었습니다. 예시 글도 하나의 짧은 섹션만 사용해 새로운 글을 작성할 때 따라갈 공통 기준이 없었습니다.

### 판단

누적 개발 문서는 전체 프로젝트 이력을 한곳에서 보는 용도로 유지합니다. 실제 사이트 Log에는 작업마다 MDX 파일 하나를 만들어 태그로 찾을 수 있게 합니다. 두 문서는 같은 내용을 일부 공유하지만 읽는 목적이 다릅니다.

### 추가

- 공식 사이트 작업 로그 템플릿 `docs/templates/WORK_LOG_TEMPLATE.md`
- 1차 MVP, 2차 품질·SEO, 3차 폰트·콘텐츠, 4차 모바일 작업 로그 MDX
- 템플릿에 작업 전 상태, 원인, 추가·수정·삭제, 초보자 설명, 자동·수동 검증, 관련 파일, 남은 점 항목

### 수정

- 기존 placeholder 로그 6개를 `기록한 이유 → 핵심 내용 → 왜 중요할까 → 확인한 내용 → 다음에 할 일` 순서로 통일
- 실제 경험이 없는 글은 PLACEHOLDER 주석과 미완료 체크를 유지
- 썸네일 없는 작업 로그가 목록 앞에 추가되면서 발생한 LCP 경고를 해결하기 위해 첫 번째 이미지가 있는 글을 eager 로딩하도록 수정

### 삭제

- 로그 파일 삭제 없음
- 기존 로그의 제각각인 단일 섹션 구성은 공통 구조로 교체

### 초보자 설명

코드 변경 기록과 사이트에 게시하는 글은 목적이 다를 수 있습니다. 누적 문서는 전체 흐름을 빠르게 찾는 목차이고, MDX 작업 로그는 한 작업을 독립적인 글로 읽고 `Codex` 같은 태그로 모아보는 기록입니다.

### 검증 결과

- 실제 1~4차 작업과 이번 템플릿 정비 작업을 포함해 사이트 Log가 총 11개가 됐습니다.
- `/log?tag=Codex`에 실제 작업 로그 5개가 함께 표시됐습니다.
- 새 작업 로그 상세 페이지에는 표준 섹션 10개가 순서대로 표시됐습니다.
- 기존 `mdx-first` 상세 페이지에는 일반 학습 로그용 공통 섹션 5개가 표시됐습니다.
- 가로 스크롤 0건, 깨진 이미지 0건, 브라우저 콘솔 오류·경고 0건이었습니다.
- `npm run lint`, `npm run type-check`, `npm run format:check`, `npm run build`를 모두 통과했습니다.
